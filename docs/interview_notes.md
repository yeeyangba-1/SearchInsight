# SearchInsight 面试讲解稿

## 1. 项目一句话介绍

SearchInsight 是一个基于 Multi-Agent 工作流的 AI 搜索效果诊断与优化平台，可以分析用户 Query、AI 回答、知识库召回片段和用户反馈，识别 Bad Case，并输出优化建议、图表和诊断报告。

## 2. 为什么做这个项目

现在很多 AI 搜索和 RAG 问答系统上线后，真正难点不是“能不能回答”，而是“回答是否准确、是否完整、是否基于知识库、用户为什么不满意”。所以我做了 SearchInsight，把搜索日志转成可分析的质量指标，帮助定位问题出在检索、知识库、生成还是 Prompt 约束。

## 3. 整体流程

用户上传 AI 搜索日志后，系统会先检查字段完整性，再清洗日志，然后做 Query 类型分类和 Bad Case 识别。接着系统会统计整体质量指标、生成图表，对疑似低质量样本做 LLM Judge 语义复核，最后生成一份 Markdown 诊断报告。

可以简单概括为：

上传日志 -> 字段检查 -> 日志清洗 -> Query 分类 -> Bad Case 识别 -> LLM Judge -> 图表 -> 优化建议 -> 报告。

## 4. 8 个 Agent 分别做什么

TASK Agent：理解用户的搜索诊断任务，明确要分析 Query 类型、Bad Case、知识库利用和优化建议。

QUALITY Agent：检查日志字段是否完整，重点看 query、answer、retrieved_docs、user_feedback、clicked、created_at。

CLEAN Agent：清洗搜索日志，处理空值、重复 query、用户反馈格式等问题。

EDA Agent：做统计分析，比如总 Query 数、Bad Case 占比、Query 类型分布、Bad Case 类型分布。

VIZ Agent：生成诊断图表，包括 Query 类型分布、Bad Case 类型分布、正常 / Bad Case 占比。

EVAL Agent：做回答质量评估，先用规则筛低质量样本，再用 LLM Judge 做语义复核。

INSIGHT Agent：把统计结果转成优化建议，比如补知识库、优化 Prompt、调整检索规则。

REPORT Agent：生成 AI 搜索效果诊断与优化报告。

## 5. Bad Case 怎么判断

我先用规则做第一层判断，因为规则稳定、成本低、可解释。

- answer 太短：回答过短
- retrieved_docs 为空：检索结果为空
- user_feedback 为不满意：用户不满意
- query 和 answer 关键词明显不匹配：疑似答非所问
- retrieved_docs 有关键信息但 answer 没体现：知识库未利用
- 以上都没触发：正常

这套规则不追求一步到位，而是先把搜索质量诊断闭环跑通。

## 6. LLM Judge 为什么有用

规则判断能发现明显问题，但语义能力有限。比如回答看起来有关键词，但实际上没有回答用户问题；或者检索片段里有关键事实，但回答只泛泛而谈。LLM Judge 可以补充语义判断，评估 answer 是否回答了 query、是否利用 retrieved_docs、是否遗漏关键信息。

## 7. 为什么不是所有功能都用大模型

因为不是所有任务都适合大模型。字段检查、清洗、统计、画图这些任务用代码更稳定、更便宜、更可控。大模型适合处理语义判断，所以我只对疑似低质量样本调用 LLM Judge，避免每条日志都调用导致成本过高。

## 8. 如何接入已有 RAG / 教学平台

如果接入已有 RAG 系统，只需要把线上日志导出成固定字段：query、answer、retrieved_docs、user_feedback、clicked、created_at。SearchInsight 可以作为诊断层，不替代原搜索系统，而是分析搜索效果，输出 Bad Case、质量指标和优化建议。

如果接入教学平台，可以用它分析学生提问、AI 答复、知识库召回片段和学生反馈，找出哪些课程知识点覆盖不足、哪些回答容易答非所问。

## 9. 当前局限

当前项目主要是规则版 + 小样本 LLM Judge，示例数据是模拟数据，还没有接真实搜索引擎、数据库、用户系统和完整 RAG 链路。LLM Judge 的结果也需要后续用人工标注做一致性验证。

## 10. 后续优化

后续可以接入真实 RAG 日志，增加人工标注闭环，做 Prompt A/B 测试，分析知识库覆盖率，并把历史诊断结果保存到 SQLite，方便比较多次优化前后的变化。

## 11. 高频面试问答

**Q1：这个项目解决什么问题？**  
A：解决 AI 搜索上线后质量不可见的问题，把用户问题、AI 回答、知识库召回和用户反馈转成 Bad Case 类型、质量指标和优化建议。

**Q2：为什么要做 Query 分类？**  
A：因为不同类型的问题优化方式不同。比如技术问题答非所问，可能要优化技术文档和检索；售后问题不满意，可能要补标准答案。

**Q3：Bad Case 类型有哪些？**  
A：包括正常、回答过短、检索结果为空、用户不满意、知识库未利用、疑似答非所问。

**Q4：为什么用 Multi-Agent？**  
A：这里的 Agent 更像职责清晰的工作流节点，用来拆分任务理解、质量检查、清洗、统计、评估、洞察和报告，不是为了夸大智能性。

**Q5：这是不是普通函数也能做？**  
A：单个规则判断可以用函数做，但我保留 Agent 工作流，是为了让整个诊断流程更清晰，也方便后续替换某个节点，比如把 EVAL 节点升级成更强的评估器。

**Q6：LLM Judge 判断什么？**  
A：判断回答是否回答了问题、是否利用了检索片段、是否遗漏关键信息，以及问题主要出在检索、知识库、生成还是 Prompt 约束。

**Q7：为什么不每条都调用 LLM？**  
A：成本高且没必要。先用规则筛出疑似低质量样本，再让 LLM Judge 复核，更符合工程上的成本控制。

**Q8：项目输出对业务有什么价值？**  
A：它能告诉团队哪些 query 类型风险最高、Bad Case 集中在哪些原因、应该优先补知识库还是优化 Prompt。

**Q9：如果 LLM API 不可用怎么办？**  
A：系统会 fallback 到规则评估，页面和报告仍然能正常生成，保证演示和基础诊断不受影响。

**Q10：你后续最想优化什么？**  
A：我会优先接真实 RAG 日志和人工标注，用标注结果验证 Bad Case 识别和 LLM Judge 的准确性。
